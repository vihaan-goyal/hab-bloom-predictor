# Bloom-forecast buoy on an ESP32

This sketch runs the Narragansett Bay bloom forecast on an ESP32 chip, with no computer attached.
The forecast is the fork's release model v2: 300 small decision trees that give
**P(daily chlorophyll > 10 µg/L within the next 7 days)**. The board raises an alert when p ≥ 0.45.

The board builds the model's 23 inputs from its own daily history in the same way the training code
did. These inputs are chlorophyll, its last 4 days, its rolling means, trend, anomaly and
climatology, plus temperature, salinity, oxygen and month. The board then scores them.

**A bare ESP32 with no sensors works out of the box.** In that case it runs in DEMO mode: you type
(or stream) one line per day, and it prints the forecast.

## Files

| File | What it is |
|---|---|
| `buoy_esp32.ino` | The sketch: commands, alert outputs, sensors (each off until enabled), NVS storage |
| `bloom_model.h` | The model as C arrays. **Generated in the fork**; do not edit (see "Regenerating") |
| `features.h` | Builds the 23 features from the daily history, matching training rule for rule |
| `pss78.h` | Converts conductivity and temperature to salinity (PSS-78) |
| `selftest.h` | The boot self-test |
| `test_vectors.h` | Real data rows plus Python's answers for the self-test. Generated by `make_test_vectors.py` |
| `replay_demo.py` | Streams a real station's days to the board and compares the board with Python |

## 1. Upload (about 5 minutes)

1. Install the **Arduino IDE 2**. Go to **File → Preferences → Additional boards manager URLs** and
   paste `https://espressif.github.io/arduino-esp32/package_esp32_index.json`.
2. Open **Tools → Board → Boards Manager**, search for **esp32** and install
   **"esp32 by Espressif Systems"**.
3. Open `hardware/buoy_esp32/buoy_esp32.ino`. The other files in the folder open as tabs; leave them.
4. Select **Tools → Board → esp32 → ESP32 Dev Module**.
5. Plug in the board and pick its port under **Tools → Port** (COM3, COM5, …).
   - If no port appears, install the USB driver for the chip on your board: CP210x or CH340.
6. Click **Upload** (→).
   - If the upload stops at `Connecting....`, hold the board's **BOOT** button until the
     percentages start.
7. Open **Tools → Serial Monitor**. Set it to **115200 baud** and **Newline**.
   - Press the board's **EN** (reset) button to watch the boot.

## 2. The self-test (runs at every boot)

```
SELFTEST begin: model 300 trees, 23 features, threshold 0.45, horizon 7 d
  [names]    feature order matches bloom_model.h: PASS
  [model]    row                       C     Python       diff  decision
  [model]    B3 2013-07-04      0.998575   0.998575  +2.90e-08  ALERT/ALERT PASS
  ...  (8 real station-days: 2 clear alerts, 2 near the 0.45 line, 2 clear no-alerts, 2 with missing inputs)
  [features] 8 days x 23 features vs fork columns: max |diff| 1.91e-06  PASS
  [pss78]    S(R=1,15C,0)=35.0000 (35)  S(R=1.888091,40C,10000dbar)=40.0000 (40)  PASS
SELFTEST PASS (0 failures)
READY mode=DEMO. ...
```

The self-test makes four checks:

- **model:** the chip's probability minus Python's must be smaller than 0.002, and both must make
  the same ALERT/idle decision.
- **features:** 29 real days from station B3 go through the chip's feature code. The last 8 days
  must equal the training table's columns.
- **pss78:** the salinity formula must reproduce the two official UNESCO check values.
- **names:** the feature order in `features.h` must match the model's.

The onboard blue LED shows the result: **3 slow blinks = pass, 10 fast blinks = FAIL**.

Type `selftest` to run it again.

## 3. Demo: type days, get forecasts

Each line is one day of **daily means**:

```
day <yyyy-mm-dd> <chl ug/L> <temp C> <salinity PSU> <DO mg/L> [chl climatology]
```

- Write `nan` for a missing value. The model then uses the training median for it, as it did in
  training.
- The optional 6th number is that day's chlorophyll climatology (see Limitations).

Copy and paste these 10 real days from RIDEM station B7, August 2020, all at once:

Other commands:

| Command | Does |
|---|---|
| `status` | Mode, self-test result, days in the history, last p, ALERT/idle, climatology table |
| `hist` | Lists the stored days (at most the last 30) |
| `reset` | Clears the daily history. Calibration and climatology are kept |
| `vec <23 numbers>` | Scores a raw feature vector, in the order of `BLOOM_FEATURES` in `bloom_model.h` |
| `clim <month> <value>` | Stores the site's chlorophyll climatology for that month (`nan` clears it). `clim` alone shows the table; `climclear` erases it |
| `selftest`, `help` | Run the self-test again; list the commands |

Some details of how days are handled:

- **Repeated date:** sending the same date again replaces that day and rescores it.
- **Older date:** an older date is refused. Send `reset` first.
- **Skipped dates:** the board accepts them. "Yesterday" means the previous *row*, exactly as in
  training.

## 4. Replay a real station from the PC

`replay_demo.py` sends a station's real daily rows from the fork's
`data/narragansett_daily_features.csv` to the board. For each day it prints the board's p next to
Python's p. Python's p is computed from the same history by the same feature rules and the same
model. Any mismatch is flagged.

```bash
# close the Serial Monitor first (only one program can use the port)
~/anaconda3/python.exe hardware/buoy_esp32/replay_demo.py --port COM5 --station B3 --start 2023-07-01 --days 60
# no board: the Python path alone, compared with the fork's precomputed training columns
~/anaconda3/python.exe hardware/buoy_esp32/replay_demo.py --sim --station B3
```

Options:

- `--start` streams the 21 days before it as warm-up.
- `--clim none` leaves the climatology out, as a brand-new buoy would have to.
- The script needs `pyserial` for a board: `pip install pyserial`.

Result on 2026-10-05: `--sim` reproduces the fork's 23 training columns exactly for all 18
stations: 42,315 days, largest difference 9e-14, zero alert disagreements.

## 5. Sensors (later)

Turn a sensor on by setting its flag to 1 near the top of `buoy_esp32.ino`. Any flag at 1 switches
the board to **SENSOR mode**. In that mode the board:

- samples every 15 minutes;
- averages each local day (midnight to midnight, US Eastern);
- drops a day with fewer than **48** chlorophyll readings, as training did;
- scores each completed day automatically.

The last 30 days, the clock, today's partial sums and all calibration are kept in flash memory
(NVS), so a reboot loses nothing except the time it was off.

| Flag | Part | ESP32 pins | Library (Library Manager) |
|---|---|---|---|
| `USE_DS18B20` | DS18B20 waterproof temperature probe | data → **GPIO 4**, 4.7 kΩ from data to 3.3 V, red → 3.3 V, black → GND | OneWire, DallasTemperature |
| `USE_TSL2591` | TSL2591 light sensor (fluorometer) | SDA → **GPIO 21**, SCL → **GPIO 22**, VIN → 3.3 V, GND | Adafruit TSL2591 Library, Adafruit Unified Sensor |
| (with TSL2591) | Blue excitation LED | **GPIO 25** → 1 kΩ → NPN transistor base; LED + resistor on the collector side (do not drive a bright LED straight from the pin) | — |
| `USE_EZO_EC` | Atlas EZO-EC conductivity circuit, **I2C mode**, address 0x64 | SDA → **GPIO 21**, SCL → **GPIO 22** (shared with the TSL2591), VCC → 3.3 V, GND | none (Wire) |
| `USE_PH` | Analog pH module | Po → voltage divider (10 kΩ / 20 kΩ, 5 V → 3.3 V) → **GPIO 34**; module V+ → 5 V, G → GND | none |
| always | Alert relay module | IN → **GPIO 26**, VCC → 5 V (VIN pin), GND; set `RELAY_ACTIVE_LOW = true` for an opto relay | — |
| always | Alert light | the onboard LED on **GPIO 2** | — |
| `USE_WIFI` | Wi-Fi push alerts (ntfy.sh) + internet clock | — | none |

Notes on the sensors:

- **EZO-EC:** the EZO ships in UART mode. Switch it to I2C as in Atlas's datasheet: short PGND to
  TX while powering it up.
- **Salinity:** the sketch sets EZO temperature compensation to 25 °C, which means no compensation.
  The EZO then reports conductivity at the water's real temperature. The sketch converts that to
  salinity with PSS-78 using the DS18B20 temperature. **Without the DS18B20, salinity stays `nan`.**
- **pH:** pH is logged in the daily line but is **not** a model input.

Sensor commands:

| Command | Does |
|---|---|
| `read` | Takes one sample line now (not stored) |
| `date 2026-10-05 14:30` | Sets the clock (needed without Wi-Fi; the board has no battery-backed clock) |
| `blank` | With the cuvette full of filtered seawater: stores its signal as zero chlorophyll |
| `chlk <k>` | Sets µg/L per fluorometer count, from a dilution series against a sonde or lab value |
| `gain l\|m\|h\|x` | Sets the TSL2591 gain. Redo `blank` and `chlk` after changing it |
| `cal686`, `cal918` | pH probe in the 6.86 buffer, then in the 9.18 buffer. `cal` shows the calibration; `calclear` erases it |
| `wifi <ssid>`, `wifipass <password>`, `ntfy <topic>`, `ntfytest` | Wi-Fi alerts (`USE_WIFI 1`). Stored in NVS, never in the code |

How Wi-Fi alerts work:

- The buoy sends **harbor bulletins** (plain-language messages), each also printed as `MSG <title> | <text>`:
  - **Bloom WARNING** when the alert turns on: risk, today's chlorophyll, and suggested actions (shellfish growers:
    plan early harvest, hold seed; hatcheries: switch to stored or filtered intake; managers: start phytoplankton
    and toxin sampling), plus the honest false-alarm rate (about 1 per site per season, fork findings §31).
  - **All clear** when the risk drops below 0.45 again.
  - **Bloom detected** at a bloom onset: daily chlorophyll above 10 µg/L after 5 stored days at or below 10
    (the event definition of the harbor-warning test), so a bloom hovering around 10 is not announced every dip.
  - **Buoy check needed** when a day is dropped for too few readings (sensor, power or fouling problem).
- SENSOR days push every bulletin to `https://ntfy.sh/<topic>`. Demo `day` lines print them but never push.
- `site <name>` sets the name used in bulletins (e.g. `site Newport-Harbor`); it is kept in NVS.
- Install the ntfy app and subscribe to the same topic.
- ntfy topics are public, so pick a topic name nobody would guess.
- No board? `python replay_demo.py --sim --station B3 --start 2023-05-01 --days 150 --bulletins` prints the
  bulletin timeline a real season would have produced (same rules as the firmware).

## 6. Limitations: read before quoting results

1. **Climatology.** In training, `chl_climatology` is the station's average for the same 15-day
   window in *earlier years*. A new buoy has no earlier years.
   - The board uses the `clim <month> <value>` table if you load one. Good sources are the site's
     past data, or the fork's values for the nearest RIDEM station.
   - Otherwise it uses `nan`, which becomes the training median (9.2 µg/L).
   - Over the full B3 and F4 records, dropping the climatology changes the alert decision on
     **111 of 2,913** and **133 of 4,725** days (about 3 to 4%), with p shifts up to 0.38.
   - The month table is also coarser than the 15-day bins used in training.
2. **Chlorophyll scale.** The model was trained on RIDEM sonde chlorophyll (µg/L). A DIY
   fluorometer reads raw counts, so `blank` + `chlk` must turn those counts into
   **sonde-equivalent** µg/L. Calibrate against a sonde or a lab extraction; a dye dilution only
   is not enough.
   - If the scale is off by 2x, the 10 µg/L bloom line and every chlorophyll input are off by 2x.
   - The PC tool `predict_anywhere.py` quantile-rescales chlorophyll; the board does not.
   - The planned fix is a 2-4 week side-by-side next to a RIDEM or Narragansett Bay NERR sonde
     (plan §12 in `notes/mitigation/EXECUTION_PLAN.md`). `blank` + `chlk` are fitted from those daily
     means with a target of ±20%.
3. **No oxygen sensor.** `do` and `do_lag1` are always missing, so the model uses the training
   median (7.8 mg/L). Oxygen is one of the model's inputs, so expect somewhat weaker skill than the
   fork's published numbers.
4. **The first days are thin.** Several inputs need a minimum amount of history:
   - lags need 1 to 4 earlier days;
   - `chl_roll21_mean` needs 7;
   - the 6-day trend needs 2.

   Until then those inputs fall back to the training medians. Forecasts become comparable to
   training after about 3 weeks of complete days.
5. **No ON/OFF loop rules.** The relay simply follows today's alert. The alerter's rules (recheck
   every X days, C_ok, MAX_ON, T_off, floor, handover) are not ported yet. `controlHook()` in the
   sketch is the hook for them; see the TODO there and `hardware/alerter_uno/alerter_uno.ino`.
6. **Clock.** Without Wi-Fi the clock starts again from the last saved time after a power cut.
   Send `date` again after any long outage, or days will be stamped late.

## Regenerating after a model update

```bash
# in the fork (hab-bloom-predictor-narragansett), BASE env
~/anaconda3/python.exe src/deploy/export_c_model.py      # writes release/bloom_model.h
# copy it over hardware/buoy_esp32/bloom_model.h and keep the "COPIED, NOT EDITED" note on top, then here:
~/anaconda3/python.exe hardware/buoy_esp32/make_test_vectors.py
```

## Size

ESP32 Dev Module, esp32 core 3.3.12, all flags 0: 352,322 bytes flash (26%), 24,664 bytes RAM (7%).
With USE_EZO_EC + USE_PH + USE_WIFI: 1,128,844 bytes flash (86%; Wi-Fi + HTTPS is most of it), 52,456 bytes RAM.
The model tables take about 37 KB of flash.
